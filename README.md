# Бот поддержки

Telegram-бот для клиентской поддержки: клиент сканирует QR → выбирает
категорию обращения → описывает проблему → тикет уходит менеджеру.
Дальше переписка идёт через бота, а сотрудник отвечает клиенту из личного кабинета.

## Как это выглядит

**Клиент.** Сканирует QR (`https://example.invalid/contact<bot>?start=defect`) или пишет
`/start`, выбирает категорию кнопкой, пишет суть. Получает номер обращения.
Пишет в личку — сообщения добавляются к единственному открытому обращению.
Если обращений несколько, бот предлагает выбрать нужное и сохраняет сообщение
до выбора. Клиент получает ответ сотрудника с названием обращения.

**Сотрудник.** Карточка нового обращения приходит в личку каждому активному
сотруднику и администраторам. Ответы клиента по назначенному обращению также
приходят ведущему сотруднику. Ответить и управлять очередью можно в личном
кабинете бота.

## Быстрый старт

```bash
uv sync                                   # поставить зависимости
cp .env.example .env                      # BOT_TOKEN, DATABASE_URL

uv run python -m app.migrate              # создать схему support
uv run python -m app                      # запустить бота
```

Для Excel-шаблонов FAQ используется `openpyxl`. Зависимость устанавливается командой
`uv sync`. Перед запуском обновлённого бота примените миграции:

```bash
uv run python -m app.migrate
```

Бот стартует в режиме long polling, вебхук не нужен.

## Настройка

`config/settings.yaml` — перечитывается на лету, перезапуск нужен только
для смены `timezone`.

```yaml
support:
  categories:                             # исходные ключи категорий
    - {key: defect,  title: "Не работает / брак"}
  manager_user_ids: []                    # bootstrap-менеджеры по Telegram ID
  admin_user_ids: []                      # bootstrap-администраторы по Telegram ID
```

**`key` категории после запуска менять нельзя** — старые тикеты ссылаются на
него в базе. `title` править можно в любой момент.
Актуальные категории для кнопок и QR-ссылок берутся из базы и управляются
администратором через бота.

Карточки отправляются в личку активным сотрудникам из реестра бота, а также
bootstrap-аккаунтам из `manager_user_ids` и `admin_user_ids`. Для первичной
настройки укажите Telegram ID хотя бы одного ответственного в одном из этих
списков, запустите бота и отправьте ему `/start` с этого аккаунта: бот сможет
писать пользователю только после того, как тот откроет личный чат. Дальше
администратор может приглашать сотрудников через управление сотрудниками;
приглашённый сотрудник также должен открыть бота и отправить `/start`, чтобы
активировать приглашение и получать карточки. В Telegram-группу бота добавлять
не требуется.

Секреты — только в `.env` (см. `.env.example`): `BOT_TOKEN`, `DATABASE_URL`,
опционально `SENTRY_DSN`, `LOG_LEVEL`. Отдельно `DOCKER_DATABASE_URL` — адрес
той же базы изнутри контейнера, если он отличается от локального.

## Сборка и запуск

### Из VSCode

**`Ctrl+Shift+B` — собрать и запустить бота.** Одна кнопка делает всю цепочку:

```
сборка образа → миграции → запуск (логи прямо в терминал)
```

Бот запускается в фоне, поэтому задача VS Code завершится сразу и не будет
оставаться в состоянии «Building». В её терминале видны итоговый статус и
последние строки лога.

Шаги связаны `&&`: упала сборка — миграции и запуск не побегут. После запуска
остановите только бота задачей «Остановить бота».

Остальные задачи — `Ctrl+Shift+P` → «Tasks: Run Task»:

| Задача | Что делает |
|---|---|
| **Запустить бота** | вся цепочка выше ← **Ctrl+Shift+B** |
| Состояние бота | контейнер запущен? + последние строки лога |
| Остановить бота | `docker compose stop bot` — штатно закрывает только бота |
| Собрать образ бота | только сборка, без запуска |
| Миграции (в контейнере) | `docker compose run --rm migrate` |
| Проверить всё и собрать | ruff → mypy → тесты → образ |

Локальные задачи (без Docker) рядом: `uv sync`, миграции, запуск бота
(тоже отменяется кнопкой), тесты, линт, типы.

### Из терминала

```bash
docker compose build bot
docker compose run --rm migrate            # схема support
docker compose up -d bot                   # запуск в фоне
docker compose stop bot                    # штатная остановка
```

### Если бот не поднимается

Причину видно в логе (кнопка печатает его сама):

| В логах | Что делать |
|---|---|
| `BOT_TOKEN не похож на токен бота` / `Telegram не принял BOT_TOKEN` | в `.env` плейсхолдер из `.env.example`; подставьте токен от @BotFather и запустите снова |
| `Connect call failed ('127.0.0.1', ...)` | база недоступна по адресу из `DATABASE_URL`; внутри контейнера `127.0.0.1` — сам контейнер, задайте `DOCKER_DATABASE_URL` с `host.docker.internal` |

Если задача уже завершилась, а контейнер остался — «Состояние бота» покажет
статус, «Остановить бота» погасит.

## Деплой

```bash
cp .env.example .env && $EDITOR .env       # БОЕВЫЕ значения
docker compose run --rm migrate            # схема support
docker compose up -d bot                   # на сервере — отсоединённо
```

На сервере запуск отсоединённый (`-d`): там терминала нет, а `restart:
unless-stopped` поднимает бота после перезагрузки. База — внешняя, в compose
её нет. `config/` монтируется поверх образа: правка категорий на сервере
применяется без пересборки.

## Разработка

```bash
uv run ruff check . && uv run mypy app     # линт и типы
TEST_DATABASE_URL='postgresql+asyncpg://postgres:test@127.0.0.1:5432/support_test' \
  uv run pytest                            # тесты (без TEST_DATABASE_URL интеграционные пропустятся)
```

### Диалог разработки в истории проекта

История сессий агента лежит в бакете по каталогу запуска
(`~/.omp/agent/sessions/<cwd>/`), и пикер показывает сначала только текущую
папку. Диалог, начатый из другого каталога, в проекте не виден — перенести
его можно скриптом:

```bash
scripts/sync-session.py            # новейший живой диалог → в историю проекта
scripts/sync-session.py --list     # что вообще есть
```

Дальше в VSCode, открытом на каталоге проекта: `omp --resume` и выбрать
диалог по названию (заголовок — первый вопрос диалога).

Скрипт делает снимок-форк: копирует записи диалога и пишет заголовок с `cwd`
проекта. То, что сказано после снимка, в нём не появится — чтобы догнать
хвост, запустите скрипт ещё раз. Снимок, в котором вы продолжили работу
(его тело длиннее исходного), скрипт не удаляет, а оставляет и говорит об
этом: молча стереть чужую работу хуже лишнего файла в списке.

### Экспорт диалога в текст

Чтобы отдать ход работы другому чату или модели:

```bash
scripts/export-chat.py                                  # → chat-export.md
scripts/export-chat.py --format txt                     # простым текстом
scripts/export-chat.py --title "Разработка DemoBrand-бота"   # заголовок в шапке
scripts/export-chat.py --with-tools                     # добавить вывод инструментов
```

В файл попадают реплики человека, ответы ассистента и сводки сжатий (в них —
постановка задачи и состояние работы). Вырезаются вывод инструментов и блоки
размышлений: это около 90% объёма и для внешнего читателя мусор — при 3.8 МБ
исходной сессии файл выходит ~240 КБ.

Секреты вычищаются всегда: токен бота и пароль из строки подключения
заменяются на плейсхолдеры. Диалог про бота по определению содержит и то и
другое, поэтому это не опция, а часть экспорта.

Границы реплик помечены строкой из `=`: ответы ассистента сами полны
markdown-заголовков (он пишет этой же разметкой документацию), и `### Ты`
в таком тексте неотличим от настоящей метки роли.

## Устройство

```
app/
  __main__.py        точка входа: конфиг → база → бот
  config.py          YAML с горячей перезагрузкой + секреты из .env
  domain.py          TicketState
  clock.py           время через Clock — в тестах ManualClock
  logging.py         loguru + Sentry, белый список полей
  errors.py          глобальный обработчик: падение хендлера не роняет бота
  migrate.py         forward-only раннер миграций
  db/                движок, сессии, модели
  repositories/      SQL, без бизнес-логики
  services/          логика тикетов и рассылка уведомлений
  bot/
    factory.py       сборка Bot и Dispatcher
    callbacks.py     формат callback_data: сборка и разбор в одном месте
    keyboards.py     клавиатуры из конфига
    filters/         «кто менеджер», «чат менеджеров», «личка»
    middlewares/     контекст лога, перезагрузка конфига, сессия БД
    handlers/        клиентский сценарий и менеджерские команды
migrations/          источник правды схемы (модели — её отражение)
docs/                требования, устройство, инструкция менеджеру
```

Слои не перепрыгиваются: хендлер → сервис → репозиторий. Хендлер не ходит
в базу напрямую, сервис не знает про aiogram-фильтры, репозиторий не шлёт
сообщений.
